## 1. 功能概述

### 1.1 功能背景

在 IoT 智能控制系统中，设备可能因为网络故障、电源断开等原因离线。为了提升用户体验，需要实时检测设备在线状态，并在前端直观展示。

系统中存在两类设备：
- **常在线设备**：持续连接 WiFi/MQTT（如喂食器、灯控开关），使用固定 5 分钟超时判定离线
- **低功耗设备（lowPower）**：运行在 DeepSleep 模式（如 AC01 温控器），定期唤醒后短暂在线即休眠，固定 5 分钟超时会导致误判离线

### 1.2 功能描述

当 control 类型设备超过指定时间未发送 MQTT 状态信息时：
- **常在线设备**：超过 5 分钟（`OFFLINE_TIMEOUT`）无状态更新则标记离线
- **lowPower 设备**：连续 3 个唤醒周期无状态更新才标记离线（超时 = 唤醒周期 × 3）
- 系统自动标记设备为离线状态
- 前端设备组图标显示为灰色（灰度化效果）
- 显示离线提示标识
- API 接口返回设备在线状态信息

### 1.3 功能目标

| 目标         | 描述                                                      |
| ------------ | --------------------------------------------------------- |
| 实时检测     | 每30秒检查一次设备活跃状态                                |
| 常在线超时   | 超过5分钟无状态更新则标记离线                             |
| lowPower超时 | 超过3倍唤醒周期无状态更新才标记离线                       |
| 前端展示     | 离线设备组图标显示灰色                                    |
| 状态同步     | 通过 WebSocket 实时同步离线状态                           |

### 2.3 lowPower 离线检测机制

#### 2.3.1 设计原理

DeepSleep 设备（如 AC01）以固定周期唤醒，每次在线约 15 秒后重新休眠。如果使用固定 5 分钟超时：

- 唤醒周期 5 分钟 → 设备恰好在线 15 秒，5 分钟超时 + 30 秒检查间隔几乎必然误判离线
- 设备在前端反复闪烁 在线→离线→在线

解决方案：**lowPower 设备的超时时间 = 唤醒周期 × 3**

- 唤醒周期 5 分钟 → 超时 15 分钟，正常每 5 分钟唤醒刷新，永不误判
- 连续丢失 3 次唤醒（15 分钟无消息）→ 判定离线
- 修改唤醒周期为 N 分钟 → 超时自动调整为 N×3 分钟

#### 2.3.2 唤醒周期获取

系统从 devices.json 中读取 lowPower 设备组的"唤醒时间"data 单元的 status 值：

```json
{
  "AC01": {
    "lowPower": true,
    "units": [
      { "id": "..._kg01-6432", "type": "control" },
      { "id": "..._huanxingshijian-7645", "name": "唤醒时间", "status": "5", "type": "data" }
    ]
  }
}
```

匹配逻辑：`unit.name === '唤醒时间' || unit.id.includes('huanxingshijian')`

#### 2.3.3 超时计算规则

```
getOfflineTimeout(unitId):
  遍历设备配置查找 unitId 所属设备组
  ├─ 设备组有 lowPower: true
  │   ├─ 找到"唤醒时间"单元（status 为分钟数）
  │   │   → 超时 = parseInt(status) × 3 × 60 × 1000 ms
  │   └─ 无"唤醒时间"单元
  │       → 超时 = OFFLINE_TIMEOUT × 3（兜底 15 分钟）
  └─ 普通设备
      → 超时 = OFFLINE_TIMEOUT（5 分钟）
```

```javascript
// 获取设备的离线超时时间
function getOfflineTimeout(unitId) {
  for (const [groupName, groupConfig] of Object.entries(deviceConfigs)) {
    if (groupName === 'lastUpdated' || !groupConfig?.units) continue;
    if (groupConfig.lowPower === true) {
      const unit = groupConfig.units.find(u => u.id === unitId);
      if (unit) {
        const wakeupUnit = groupConfig.units.find(u =>
          u.name === '唤醒时间' || u.id.includes('huanxingshijian')
        );
        if (wakeupUnit && wakeupUnit.status) {
          const wakeMinutes = parseInt(wakeupUnit.status) || 5;
          return wakeMinutes * 3 * 60 * 1000; // 3倍唤醒周期
        }
        return OFFLINE_TIMEOUT * 3; // 兜底3倍默认超时
      }
    }
  }
  return OFFLINE_TIMEOUT; // 普通设备
}

// 检查设备是否离线
function checkOfflineDevices() {
  const now = Date.now();
  for (const [unitId, lastActive] of Object.entries(deviceLastActive)) {
    const timeout = getOfflineTimeout(unitId);
    if (now - lastActive > timeout) {
      broadcastOfflineStatus(unitId);
    }
  }
}
```

## 7. 故障排查

### 7.1 常见问题

| 问题 | 可能原因 | 解决方案 |
| --- | --- | --- |
| 常在线设备不显示离线 | OFFLINE_TIMEOUT 配置过大 | 检查 .env 配置 |
| lowPower 设备频繁显示离线 | 唤醒时间单元 status 值不正确 | 检查 devices.json 中"唤醒时间"的 status 值 |
| lowPower 设备永不显示离线 | lowPower 标记未设置 | 检查 devices.json 中设备组是否有 `lowPower: true` |
| WebSocket连接失败 | 端口未开放 | 检查防火墙和端口映射 |
| 离线状态不同步 | MQTT连接异常 | 检查MQTT Broker状态 |
| 修改唤醒时间后超时未更新 | 服务未重启 | 重启 Node 服务重新加载 devices.json |

| 要点 | 说明 |
| --- | --- |
| 仅检测 control 类型 | state/data/text 类型设备不参与离线检测（`updateDeviceActive` 中过滤） |
| 动态超时 | `getOfflineTimeout()` 每次检查时实时计算，修改唤醒时间后下次检查即生效 |
| 两个服务独立检测 | server-status-ws.js 负责前端 WebSocket 推送，server-control-tcp.js 负责 API 状态查询 |
| 边界值处理 | 使用 `>` 而非 `>=`，间隔正好等于超时时不触发离线 |
| 兜底机制 | lowPower 设备组无"唤醒时间"单元时使用 `OFFLINE_TIMEOUT × 3`（默认 15 分钟） |

### 8.2 已知限制

| 限制 | 说明 | 影响 |
| --- | --- | --- |
| 仅 control 类型检测 | state/data 类型设备不显示离线 | wdj 温度传感器、shg 传感器等永远不显示离线 |
| server-control-tcp.js 不订阅 MQTT | 控制服务的 `deviceLastActive` 仅在初始化时设置，之后不更新 | `/api/status` 接口的在线状态可能不准确，以前端 WebSocket 推送为准 |
| 唤醒时间需手动维护 | 修改唤醒时间后需同步更新 devices.json 和固件中的值 | 如不一致，离线检测使用 devices.json 中的值 |
